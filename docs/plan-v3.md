## 1. 立论必须改：豆包不是「结构上做不到」

### 1.1 v2.0 的论证已经过期

v2.0 第 2 节写了三张表，论证「A 类：没有状态 / B 类：没有工具执行 / C 类：输出是文本」，结论是豆包这类产品**结构上不可能**做到。

这个论证在 2026 年已经不成立了。问答型产品普遍具备：工具调用、联网检索、Artifacts（可交互产物）、跨会话记忆。把它们说成「没有工具、没有状态」，是低估对手，也会让答辩时被一句话问倒。

### 1.2 真正的差别在哪

不是「能不能」，而是「**做这件事的默认产物是什么**」。

| 维度 | 问答型 AI | 本项目 | 差别性质 |
|---|---|---|---|
| 状态 | 会话内上下文，会话结束即散 | 结构化 Itinerary，可存库、可分支、可回滚 | 产物形态差异 |
| 工具 | 有，但调用发生在「回答过程中」 | 调用发生在「状态变更前」，结果必须写进字段 | 时序与约束差异 |
| 校验 | 没有独立的校验层，模型自己说合理 | 8 条规则是纯函数，与模型完全解耦 | **架构差异** |
| 证据 | 只能「声称」合理 | 每次检查都有 checked 次数与 detail | **可复现性差异** |
| 局部编辑 | 重写整段文本，语义漂移 | `item_id` 可寻址，改一项不动其余 | 数据结构差异 |
| 数据可信度 | 无法标注哪些是猜的 | `confidence: verified / estimated / unknown` | **诚实度差异** |

### 1.3 一句话（换过论据的版本）

> 问答 AI 给你一份**读起来合理**的行程；本项目给你一份**可以逐条验算**的行程。
>
> 差别不在于模型聪不聪明，而在于**结果有没有一个独立于模型的东西替它作证**。

**必须承认的边界**：这不是技术护城河。任何人都能写一个校验器。真正的壁垒是「规则设计得对不对 + 数据够不够准 + 修复收敛得好不好」，这三件事很脏、很慢、很难抄。

## 2. 四条设计原则

v2.0 的三条保留，新增第四条。

1. **行程是数据结构，不是文本。** 每个活动有 `id`、`start_time`、`lat/lng`、`locked`，才能被寻址、被计算、被局部修改。
2. **事实来自数据源，想象来自模型。** `poi_id` 必须能反查；模型不碰坐标、价格、营业时间。
3. **校验器是 agent 的物理引擎。** 生成 → 校验 → 定向修复 → 再校验，通过才算完。
4. **未知不等于通过（新增）。** 没有营业时间数据的点，不能算「营业时间检查通过」，只能算「未覆盖」。这一条决定了整个系统的诚实度，落地方式见 3.2 与 4.2。

## 3. 数据模型：v3.0 改了 5 个地方

| 变更 | 字段 | 为什么 |
|---|---|---|
| 新增 | `opening_hours.confidence` | 区分「核实过 / 估算 / 未知」。没有这个字段，校验器只能把 null 当通过 |
| 新增 | `item.weather_sensitive` | 室内外不是靠 category 猜的，由数据源标注 |
| 修改 | `day.summary.poi_count` | 只统计 `type=activity`，不再把餐厅算成「景点数」 |
| 修改 | `feasibility.rules[].covered` | 与 `checked` 分开：checked 是「检查了几次」，covered 是「有数据可查的几次」 |
| 约定 | 跨零点时间 | `close < open` 视为跨零点（如 19:00–02:00），统一归一为 `close + 1440` 再比较 |

**不变的部分**：`transit` 仍是一等公民；`locked` 仍是局部编辑的基础；`unscheduled` 仍是必需产物；时间仍用 `"HH:mm"` 本地字符串。

## 4. 八条规则：三条被改写

| # | code | 判定 | severity | 可自动修 | v3.0 变化 |
|---|---|---|---|---|---|
| 1 | `TIME_OVERLAP` | 后项 start ≥ 前项 end（含 transit 条目） | error | 是（整天重排） | 不变 |
| 2 | `OUTSIDE_OPENING` | 落在开放时段内且非闭馆日 | error | 是（按开门时间顺延） | **跨零点归一**；未知数据不计入 |
| 3 | `GEO_SCATTER` | 单日最大跨度 ≤ 25km，通勤 ≤ 90min | warning/error | 是（移出最远点） | **> 50km 升级为 error** |
| 4 | `BUDGET_EXCEEDED` | 总花费（含住宿）≤ 预算 | error | 是（删最贵项 + 住宿降档） | 不变 |
| 5 | `OVER_PACE` | active_min ≤ 档位上限，景点数 ≤ 上限 | warning | 是（删末项） | **只数 activity** |
| 6 | `BOOKING_RISK` | 需预约且未预约 | info | 否 | 不变 |
| 7 | `WEATHER_CONFLICT` | 恶劣天气 × 户外项目 | warning | 是（换室内备选） | **默认不参与**，见 4.3 |
| 8 | `TRANSIT_UNREACHABLE` | 单段 ≤ 120min / 60km | warning | 否 | 不变 |

### 4.1 为什么地理跨度要升级为 error

v2.0 把 `GEO_SCATTER` 定为 warning。实测下来，一份「成都 4 天」的行程里出现了单日 54.2km 的跨度，仍然显示「8/8 通过」——这等于自己打自己的脸。

修法不是改文案，是改判定：**超过阈值两倍（市内 50km）就不是「提醒」，而是「这一天根本走不通」**，必须是 error，必须被修复。

### 4.2 为什么「未知」不能算通过

本地数据集里，有一部分 POI 的营业时间只能估。如果校验器把「没有数据」当成「检查通过」，那 8/8 就是假的。

实现上分成两个计数：

- `checked`：这条规则跑了多少次比较；
- `covered`：其中有多少次**真的有数据**可比。

凭证上显示「营业时间已知 10/10」或「8/12」，用户一眼就能看出哪部分是验证过的、哪部分是假设。这比一个漂亮的 100% 有用得多。

### 4.3 为什么天气默认不参与

v2.0 假设接 Open-Meteo。第一版没有接，但为了「让第 8 条规则看起来在工作」，曾经用确定性模拟数据生成天气——结果 4 天里 3 天有雨，修复器把所有户外项目都换成了室内。

这是**用假数据驱动真决策**，比不检查更糟。v3.0 的处理是：默认 `weatherSource = none`，凭证上明确写「无天气数据，未校验」；需要验证这条规则时，用 What-if 里的「第 2 天暴雨」显式触发。

## 5. 生成管线（已实现）

| 阶段 | 输入 | 输出 | 关键约束 |
|---|---|---|---|
| INTAKE | 一句话 | `meta` | **缺目的地就停下来问**，绝不默认一个城市 |
| RESEARCH | `meta` | POI 池 + 打分 | 只从数据集取，不生成任何 POI |
| OUTLINE | 池 | 每天去哪些点 | 地理聚类 + 偏好加权；**> 30km 的郊县点不进排程** |
| SCHEDULE | 分天方案 | 带时间的 items | 时间由程序累加，模型不碰数字 |
| VERIFY | Itinerary | violations + 凭证 | 纯函数，零 LLM |
| REPAIR | violations | 修好的 Itinerary | 最多 3 轮，无改善即停 |
| RENDER | Itinerary | 时间轴 / 地图 / 凭证 | 纯前端 |

SCHEDULE 的核心只有一段（伪代码）：

从 09:30 开始，按地理最近邻顺序遍历当天点位：先算路网通勤，到达时刻取「当前时刻 + 通勤」与「开门时间」的较大值；如果到达时刻加停留时长已经超过打烊时间，就把它下沉到候选池；否则写入一段 transit 和一段 activity，游标推到活动结束。

**模型不碰时间数字，就不可能出现「11:00 结束、10:30 开始」。** 实测 49 个单测里，`TIME_OVERLAP` 在生成阶段的一次通过率是 100%——因为它在结构上不可能发生。

## 6. 修复循环（已实现）

每轮按固定顺序执行，前一步的输出是后一步的输入：

| 顺序 | pass | 修什么 |
|---|---|---|
| 1 | `fixOverlap` | 整天按顺序重排，消除重叠 |
| 2 | `fixClosedDays` | 闭馆日的项下沉候选池 |
| 3 | `fixTooLong` | 开放时长装不下的项下沉 |
| 4 | `fixOpeningClamp` | 按开门时间顺延整天 |
| 5 | `fixGeo` | 跨度超限时反复移出最远点（最多 4 次/天） |
| 6 | `fixPace` | 超时长 / 超点位数时删末项 |
| 7 | `fixBudget` | 删最贵项，仍超则住宿降档为青旅 |
| 8 | `fixWeather` | 户外换室内（仅在显式注入天气时） |

三个刹车：**轮数上限 3**、**patch 后必须重新 verify**、**本轮 error 没下降就停**。三轮仍不收敛时降级为「每天 2 个点」的最小可行行程，并在界面上说明砍了什么。

另有一个**润色轮**：error 清零后，如果还有「可自动修复」的 warning（跨度过大、节奏超限），再跑一次清理。理由是这些提醒虽然不阻断交付，但留着就是噪音。

## 7. 规划 vs 实际：4 处主动偏差

| v2.0 规划 | 实际实现 | 理由 |
|---|---|---|
| Next.js 15 + App Router | Vite + React 19 + TS | 第一版没有服务端逻辑（无 DB、无鉴权、无 API 代理），SSR 是纯成本。核心资产是校验器与数据模型，与框架无关。迁移成本可控 |
| Supabase + Drizzle | localStorage | 单用户场景，持久化只需要「刷新还在」。接 Supabase 属于 P2 |
| 高德 Web 服务 API | 本地 POI 数据集（72 个点，5 城） | 没有 key，也不想让项目因为没有 key 就跑不起来。`GeoProvider` 接口已留好，换实现不动业务代码 |
| GLM-5.3-Flash 负责全流程 | 规则引擎 + 可选 GLM（只做 INTAKE） | 同 4.3：没有 key 时不能让产品停摆。模型接入点收窄到「理解需求」一件事，其余全部确定性计算 |

**这不是「简化版」，而是把可验证的核心先做实。** 一份没有校验器的 LLM 行程生成器，和一个没有 LLM 的校验器，后者更接近这个项目的主张。

## 9. 实现过程中发现的 7 个规划漏洞

这一节是 v3.0 真正的价值：**每一条都是写代码时才暴露的，靠读规划书永远发现不了。**

**① 用模拟天气驱动修复。**
现象：4 天行程里有 3 天被判「有雨」，所有户外点被换成室内，行程面目全非。
根因：为了「让天气规则看起来在工作」，用确定性随机生成了天气。
修法：默认关闭天气维度，凭证上写「未校验」；需要时用 What-if 显式触发。

**② 郊县 POI 被塞进市区那一天。**
现象：成都某天跨度 54.2km，仍显示 8/8。
根因：k-means 按地理聚类，青城山（60km）被并进最近的簇。
修法：> 30km 的点不进自动排程，统一进候选池并标注「郊县一日游」。

**③ 夜市的营业时间永远判错。**
现象：九眼桥（18:00–02:00）只要被排进计划，必然产生一个 error，修复器无法修，最终触发降级，整份行程被砍到每天 2 个点。
根因：`close < open` 时直接比较分钟数，02:00 = 120 < 19:00 = 1140。
修法：跨零点归一（`close + 1440`）。一条 3 行的修正，救回了整份行程的质量。

**④ 用餐时长校验与插入时长不一致。**
现象：晚餐被排到 19:49–21:04，而餐厅 21:00 打烊。
根因：选店时按 45 分钟校验，插入时按 75 分钟写入。
修法：校验与写入用同一个 `duration`，且必须把通勤时间算进到达时刻。

**⑤ 一天只有夜市。**
现象：某天从 17:46 开始，因为当天只有九眼桥和玉林路。
根因：OUTLINE 按分数选点，某个簇恰好全是夜间项。
修法：每天保底 2 个「17:00 前开门」的点，不够就从邻近候选补。

**⑥ 缺目的地时仍然生成了一份成都行程。**
现象：输入「带娃去哪好」，系统默默按成都排了 3 天。
根因：`intake` 把缺失字段记进 `missing`，但编排器没有消费它。
修法：目的地是唯一不能猜的字段，缺失就抛 `NeedsClarification`，界面弹出城市选择。
**这一条是产品事故级的**：猜错目的地，整份行程都是废的。

**⑦ 「提醒数 3~8」是个坏指标。**
现象：v2.0 把「每份行程 3~8 条 warning」当作质量目标。
根因：这个指标可以被制造——多写几条无害提醒就能达标，而真正的问题是「有没有覆盖到」。
修法：主指标换成覆盖率（POI 可反查率、营业时间已知率）与 error 收敛速度；warning 数量只作为观察项。

## 12. 五分钟版

目标：输入旅行需求，输出一份「可以证明它走得通」的行程。

立论：不是「问答 AI 没有工具」，而是「它的产物不可验算」。本项目 = 可寻址状态 + 确定性校验 + 可复现证据。

三条硬规则：模型不碰时间、距离、加总；POI 必须能反查，查不到就删；没有数据等于未覆盖，不等于通过。

核心闭环：INTAKE（缺目的地就问）→ OUTLINE（分天分区，郊县下沉）→ SCHEDULE（程序累加时间）→ VERIFY（8 条规则）→ REPAIR（3 轮定向修 + 降级）→ 凭证（8/8 + 覆盖度）。

实测：20 用例全通过，首次通过率 95%，49 个单测。

最大收获：第 9 节的 7 个坑，全是写完才发现的。
